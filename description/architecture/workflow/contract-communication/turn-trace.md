# 轮次有序轨迹设计

> **状态：** 已实现统一驻留轨迹、消息投影、显式工具记录和终态后台备份，正式及演示运行时均接入。实现与可靠性边界见[历史驻留与备份](../../system/communication-history.md)，不新增 SSE 事件类型。

所属工作流见[合同沟通智能体](readme.md)，模型上下文过滤规则见[用户消息与上下文设计](user-context.md)。

---

## 目标与结构

每个会话保存按轮次组织的执行记录，每轮以统一有序轨迹串联用户输入、用户可见阶段说明、方法调用和最终答复，保留“为什么开始某项操作、操作得到什么、接下来做什么”的阅读连续性。

不将方法调用和阶段说明分成两个独立列表后再推测顺序。每个轨迹条目具有统一递增序号、条目类型和精简内容；序号由执行记录层分配，时间只作为辅助信息，不作为唯一排序依据。

这里的“思考”指用户可见阶段说明，不是模型内部推理、原始工具参数或临时纠错轨迹。

---

## 保留内容与顺序

| 条目 | 保留内容 |
| --- | --- |
| 用户输入 | 原始文字、附件标识及必要元数据，普通提问或补充、调整的意图。 |
| 阶段说明 | `intermediate` 消息的连续文本片段，关联原 `message_id`。 |
| 方法调用开始 | `call_id`、方法名称、用途和必要的非敏感输入摘要。 |
| 方法调用完成 | 同一 `call_id`、成功或失败状态、精简结果及证据引用。 |
| 最终答复 | `final` 消息及其引用；完整答复与中断片段须明确区分。 |
| 轮次结束 | 完成、取消、被替代、拒绝或失败，保存在记录表 status 列；历史不再保存新旧轮次关联。 |

上述是内容分类，已确认字段见 [Payload 契约](../../data/communication-sqlite.md#payload-契约)，实时消息沿用事件校验，工具条目使用独立 Schema；离线 payload 的完整语义校验尚未实现。方法既可以是确定性程序，也可以是专用子智能体；其调用事实由执行层记录，不能从 `task.progress` 文本中反推。

示意顺序：

1. 用户提出对比要求。
2. 阶段说明：“先查找今年的采购合同。”
3. 方法调用开始：查询合同，`call_id=a`。
4. 方法调用完成：`call_id=a`，找到 8 份合同。
5. 阶段说明：“接下来比较付款条件。”
6. 方法调用开始：条款对比，`call_id=b`。
7. 方法调用完成：`call_id=b`，完成对比。
8. 最终答复及轮次完成标记。

并发或耗时调用分别记录开始与完成，按实际记录顺序与说明交错排列，通过 `call_id` 关联。不得为使同一调用首尾相邻而重排中间条目，也不把并发完成顺序误写成执行依赖顺序。

## 压缩与消息边界

只合并连续、属于同一 `message_id` 的文本增量。中间一旦出现方法调用等其他保留条目，后续文本形成新的片段，即使仍属于同一消息，也不能跨过该条目合并。

`message.completed` 用于确认消息完成及完整内容，不能据此把前后片段移动到一起或将全文重复追加到轨迹。消息级完整文本可作为便于展示的投影，但有序轨迹仍保留原交错位置。

历史 payload 不单设 `messages`，每个 trace 消息条目直接携带最终状态与引用。同一消息的各片段在冻结时保持状态一致。这里不删除前端展示快照中的消息投影。

应在执行中捕获顺序，再于轮次结束时整理，而不是等有界 SSE 缓存被截断后从剩余事件重建完整记录。被取消或替代轮次同样需要明确的结束记录，不把半成品标成最终结论。

## 与现有数据的边界

- SSE 缓存短期保留原始事件，承担断线回放，不作为完整历史来源。
- 当前 `CommunicationSnapshot.messages` 按消息聚合文本，服务界面恢复；它不能代替方法与文本片段交错的轨迹。
- 轮次轨迹保存整理后的关键执行信息，方法调用摘要由执行层结构化提供；执行层通过 record_tool_call/record_tool_result 显式记录，展示执行器已接入。
- 校验进度属于 `task.progress`，原样保存到用户展示 `events`，不进入内部 `trace`；文件检查结论、剔除原因和确认问题通过普通消息进入 `trace`。业务门禁不另设轨迹类型，内部准入状态与公开消息分开管理。
- 后续模型上下文由轨迹按权限、状态和有效性筛选后组装，不直接使用全部轨迹。取消轮次只向模型保留用户问题及终止标记；调整后沿用的内容必须仍适用，不把旧半成品或失效路径作为权威事实。
- 文件名称与摘要属于 `input.files` 的后端补充元数据，不伪装成用户原文或插入助手消息。正式门禁返回完整摘要批次后，在终态前绑定原有附件身份，随任务备份并恢复；字段与失败边界见[文件引用契约](../../data/communication-sqlite.md#文件引用)。
- 私有审计与公开轨迹分开，公开轨迹不复制原始模型推理、完整敏感参数或错误堆栈。

## 存储与待定事项

持久化采用独立 SQLite 存储层，一轮任务对应一条 JSON 记录，摘要作为同序列中的独立记录，另有会话专属工作区。归属采用稳定且不复用的用户密钥，详细字段和已实现接口以 [SQLite 存储契约](../../data/communication-sqlite.md)为准。SQLite 不替代运行中继续使用的内存轨迹，记录不能与事件缓存的过期清理混为一套策略。

### 已确认：终态冻结与后台备份

> **已实现：** 任务结束后冻结轨迹，后台空闲时按契约复制落库；落库不是内存状态迁移，也不是模型上下文压缩。

1. 每轮进入终态时固定其有序轨迹。正常完成、用户方向调整、手动终止，以及拒绝、失败和过期均结束该轮；此后禁止修改轨迹或接收迟到写入。这里的“手动暂停”沿用当前取消语义，不表示可恢复并修改旧轮次。
2. 冻结轨迹继续保存在内存，供后续交互使用。用户收到终态即可阅读或继续提交问题，不等待后台落库。
3. 后台在空闲时读取冻结轨迹，按持久化契约整理、序列化并复制至 SQLite。整理仅作用于落库副本，不清空、替换、修改内存轨迹，不因备份成功而要求后续请求改为读取数据库。
4. 模型上下文如何筛选、截断或压缩，与这次备份相互独立；用户调整或终止的上下文规则不会把落库变成内存清理动作。备份应保留真实终态，不将中断片段当作最终结论。

由于备份源已经冻结，不为任务轨迹引入持续同步、内容版本比较或反复更新机制。此约束仅针对结束的单轮轨迹，不取消会话工作区自身的版本校验；后续按需生成摘要或向量也是独立动作，不改写原轨迹。

### 后台写入约束与可靠性边界

- 任务在会话中的逻辑顺序由任务创建时确定，不能使用后台整理完成或数据库写入先后推断；摘要也必须保留其真实覆盖边界。
- 写入失败允许重试，同一 `turn_id` 的重复备份不得产生重复记录，也不能覆盖不同内容；backup_task 已执行同身份、同顺序、同内容的幂等确认，不同内容拒绝覆盖。
- 后台读取来源必须是完整的冻结轨迹，不能从可能已经截断的 SSE 回放缓存重建。
- 当前不要求在发送终态前同步保存一份待整理日志。异步备份完成前若进程退出，尚未落库的数据可能丢失；不承诺零丢失。
- 当前让出终态交付周期 250 毫秒后备份，失败间隔 1 秒重试；正常关机尝试最后备份一次。完整历史尚无总容量或自动驱逐预算，详细边界见[实现说明](../../system/communication-history.md)。

### 附件与后续实现

会话附件注册时只分配 UUID 并暂存内存，明确准入后随终态备份保存到 `data/communication/upload/`，以 `/{file_id}.pdf` 引用；未准入附件只保留名称等不可用元数据。字段见[文件引用](../../data/communication-sqlite.md#文件引用)，生命周期见[附件准入与延迟落盘](../../system/communication-history.md#附件准入与延迟落盘)。[附件读取接口](../../../api/resource.md#读取已驻留会话任务的-pdf-附件)仅授权本人已驻留任务轨迹中的 accepted 文件；删除后的磁盘文件清理仍未接入。

已备份任务及其精简展示事件可跨重启保留；含 delta 的实时 SSE 回放队列仍只在当前进程内，不能据历史恢复原始流式分块。用户恢复使用 events，内部上下文仍使用 trace，详见 [Payload 契约](../../data/communication-sqlite.md#payload-契约)。轨迹总容量、保留期限和附件回收仍待定义，异常退出会丢失尚未备份的数据。

本地测试覆盖连续增量合并、跨调用不合并、并发首尾关联、完成事件不重复全文、终态冻结与迟到写入拒绝、取消和替代终态记录（模型过滤另行实现）、备份不改变内存且不阻塞下一轮、注册顺序在备份后保持不变、失败重试不重复，以及 SSE 缓存截断不破坏已记录轨迹。验证用例见 tests/test_communication_live_history.py。
