# 上下文相关性判断

> **当前状态：** 已接入正式门禁：服务端选取最近最多五轮有效历史，使用 `context-relevance-v12` 规则与随机四例构造轻量输入，通过严格 JSON Schema 约束解码和有限纠错生成判断及关联依据，交给聚合节点分级计分。核心问答上下文组装及主循环已接入，详见[主助手生成循环](agent-runtime.md)。

## 用途与边界

主要避免“继续”“接着往下说”“还有别的补充吗”等简短承接请求因自身缺少业务信息而被误拒：结合可见业务历史识别延续、调整或补充，不要求用户复述对象或完整需求。不重复进行完整的当前文字业务分类，但高权重依据必须是业务事项的延续；不核实历史结论、不执行请求、不决定整个门禁准入。

普通承接请求需要可见业务历史中的任务或答复作为依据；已经完整结束的回答仍可被要求补充。用户要求基于先前文件进一步操作但没有可见业务历史支持时，仍可判 true，但依据只能是弱关联 `prior_file_reference`，不能获得业务历史延续的高权重。二者都满足时优先使用 `history_continuation`。文件定位、可用性核验及必要澄清交给后续服务，不在门禁要求先确定具体是哪一份；不能据此宣称已找到文件。该文件意图边界与[文件文字相关性](file-text-relevance.md)一致，但计分职责不同。

`prior_file_reference` 必须同时具有明确的文档对象、先前指向和当前操作要求，不是任意前文引用的兜底。“上面第二点”“刚才的回答”“之前的思路”等没有可见业务历史支持时，不能推测为文件、列表或材料而给分。文件唯一身份不明确可以留给后续定位，但对象是否属于文档都不明确时应为 none。若可见业务历史确实能够解释同一句追问，仍可判为 history_continuation；不以关键词黑名单拒绝正常延续。

这里确认的是本轮文字中的文档指向，不核验历史上传事实。“此前提交的那份材料”等明确资料指向，即使可见历史只有纯文字，也不因缺少历史附件或无法唯一定位而降为 none。普通“先前内容”不擅自升级为文档，明确的“提交资料”也不擅自降为未知对象。

## 历史选择契约

- 在最新累计摘要之后选取历史；累计摘要本身不进入输入、不计为任务，不跨摘要边界向前凑数。
- 排除本轮及其后记录、非终态任务、expired 和整轮 rejected 历史，再取最近最多 5 轮，按从旧到新排列。拒绝任务及其派生摘要不得间接带回，见[统一排除边界](user-context.md#拒绝任务的统一上下文排除)。
- 每轮仅展示状态、用户输入和允许展示的完整最终回答，不展示中途消息、工具轨迹或中断回答。用户输入包括原文字与附件可见元数据，后端生成的文件描述不能伪装为用户原话。
- completed 可展示完整最终回答；superseded 仅在确有完整最终回答时展示，否则省略回答。cancelled、failed 只展示用户输入与对应状态标记。此处对 superseded 的轻量裁剪不改变第二层可以读取其轨迹的约定。
- 完整最终回答必须同时满足 `message_kind=final`、消息 `status=completed`；如果内部 trace 有同一消息的多个片段，后续渲染应按顺序恢复正文，不能只取最后片段。
- 有非空文字时，即使没有有效历史也运行节点，历史区使用明确空占位；由模型识别先前文件操作意图，不使用关键词硬编码放行。只有文件但没有文字时仍需有效历史，否则跳过；本轮没有任何输入也跳过。

`ConversationHistoryService.get_gate_records_locked` 在共享锁内从统一驻留队列选择历史，包含已备份与 fresh 终态任务；返回深拷贝，不改写用户记录。expired 未执行有效任务，暂不纳入模型关联输入，用户仍可查看该记录。

## 系统提示词与使用方式

源码为 `app/agent/contract_communication/business_gate/prompt/context_relevance.py`，导出：

- `CONTEXT_RELEVANCE_PROMPT_VERSION`：`context-relevance-v12`。
- `CONTEXT_RELEVANCE_SYSTEM_PROMPT`：固定系统规则，不再内嵌全部示例。

`build_context_relevance_messages(history=..., text=..., file_summaries=..., examples=None, rng=None)` 返回 system 与 user 两条消息。system 为固定规则前缀、本次抽出的四组示例及与约束解码同源的 JSON Schema；user 依次组织近 5 轮上下文、本轮文字、本轮文件摘要，各区域以分割线分隔。独立渲染器位于同目录 `context_rendering.py`，只处理调用方已选的 0～5 轮历史，不读取数据库、不发起模型请求、不修改原记录。

正式服务通过 `CommunicationEventService.get_gate_history` 校验轮次所有权及 processing 状态，再在共享锁内调用历史选择方法；注册阶段已完成密钥校验与会话加载，不在锁内重复打开会话或查库。其他内部调用方也必须遵守同一归属与选择边界。渲染器按会话顺序排序后生成本地“历史第1轮”等编号，并再次校验数量、唯一性和状态；拒绝摘要、rejected、非终态及尚未定义策略的 expired，避免把完整未过滤缓存误传为模型输入。无有效历史时渲染“本次未提供可用历史任务”，不补造记录；超过5轮不静默截断。历史上限仍为五轮，本次不扩至二十轮。

采用中文白名单字段，不序列化整个任务：

| 区域 | 展示字段 |
| --- | --- |
| 每轮历史 | 任务状态、用户文字、用户文件、适用时的助手最终回答。 |
| 历史文件 | 该轮文件序号、文件名称（display_name）、内容摘要（summary）、文件可用性。 |
| 本轮文字 | 用户原始文字；缺少时显示“本轮未提供文字”。 |
| 本轮文件 | 本轮文件序号、文件名称（display_name）、内容摘要（summary）；无文件时显示“本轮未上传文件”。 |

不额外展示原始文件名、路径、record_id/turn_id/file_id/message_id、存储顺序号、时间与耗时、引用元数据、工具轨迹、SSE、审计、检索文本和向量。只省略这些元数据字段，不对用户原文、完整最终回答或摘要正文做关键词删除；正文自身提及名称、日期或编号时仍忠于原文。

旧附件缺少 display_name/summary 时显示“未生成名称/未提供摘要”，不回退原始文件名。历史附件准入只表达已准入、不可用或未确认，不承诺实际可读取。中文状态标签对应正常完成、用户调整方向、用户手动终止、执行失败；为映射这些标签，系统提示词版本更新为 v2。

完整最终消息按内部 message_id 拼回原有片段顺序，但不向模型公开该 ID；任一片段未完成则整条省略，不输出空的回答占位。cancelled/failed 不展示回答；多个完整 final 或消息用途冲突属于无效历史，显式拒绝而非任选答案。动态字段使用安全 YAML 序列化，多行原文采用缩进块，保留换行并避免伪造顶层标题。正式 Schema 由 `schema.py` 中的 `ContextRelevanceGeneration` 统一生成。

渲染示例（虚构资料）：

```yaml
任务状态: 正常完成
用户文字: 请分析这份设备合同。
用户文件:
- 文件序号: 1
  文件名称: 加热台采购合同
  内容摘要: 约定设备交付、验收与质保责任。
  文件可用性: 已准入，实际读取仍需校验
助手最终回答: 你方是买方还是卖方？
```

提示词覆盖任务目标、输入含义、关联与反例、状态语义、历史可信边界、证据协议和 JSON 输出约定。节点仅消费文本，证据使用历史轮次、消息来源及文件序号定位，不要求未提供的 PDF 页码。

## 多轮样例与随机抽取

`prompt/context_examples.py` 为样例唯一来源，替换此前十二条压缩单轮示例。样例池是十组独立虚构完整任务，正负各五组，每组含 2～3 轮历史，采用与真实任务相同的 `render_context_relevance_input` 渲染。数据及结果由冻结对象保存；真实用户数据不参与样例生成，示例 ID 不展示给模型。

| 示例 | 结果 | 场景 |
| --- | --- | --- |
| 01 | true | 验收尾款讨论后仅问“还有别的补充吗”，结合可见历史认定延续。 |
| 02 | true | 被要求补充冷却塔签收证据后，仅上传签收单及无关培训材料。 |
| 03 | true | 对比两份续租方案，调整为只问第二份交接清单之外的拆除责任。 |
| 04 | true | 结算任务取消、失败后，以修正过的付款与折让数值重新请求余额。 |
| 05 | false | 明确搁置协议且不参考旧文件，转而要求健身计划，不能因提及旧文件判相关。 |
| 06 | false | 仓库租赁押金讨论之后，询问投标未中标保证金；退款话题相似但事项不同。 |
| 07 | false | 装修合同讨论之后，上传食堂大米报价并核对含税价；代词指向新材料。 |
| 08 | true | 根据上周保密协议追问离职义务；近期历史未展示协议不影响文件操作意图成立，不编造内容。 |
| 09 | false | 仪器维护响应讨论之后，只上传团建安排和篮球名单。 |
| 10 | false | 运输合同保价查询取消后，询问员工出差住宿报销标准。 |

每次构造一份新判断请求时，从全部十组中均匀、无放回抽四组，展示顺序也采用抽样顺序。不固定两正两负，不强制正负交替；单次允许出现 0～4 个正例。实现使用独立 `SystemRandom`，不调用全局 seed，也不根据当前问题或标签选择有利样例。

需要复现实验时，可传局部 `random.Random(seed)`，或先调用 `sample_context_relevance_examples` 再把返回的四组通过 `examples` 传给构造器；两种方式不能同时提供。显式样例须来自原池且互不重复。相同选样与相同输入的渲染保持一致；默认重复调用会重新抽样，不能再把整个 system 视为跨请求完全固定。

同次模型判断的纠错重试必须复用首次构造的消息，不重新调用构造器抽样。正式节点在私有审计中记录样例 ID、提示词版本、尝试编号、原响应、反馈及清理结果，已通过模拟连续纠错验证同次判断不重新抽样。随机示例放在固定系统规则之后，固定前缀仍稳定，但样例部分的跨请求缓存命中不再保证，这是采用随机抽样的明确取舍。

## 输出契约与执行

采用 `ContextRelevanceGeneration` 的严格 JSON Schema，字段顺序如下，禁止额外字段与隐式类型转换。

| 字段 | 约定 |
| --- | --- |
| evidence | 字符串列表，标明历史轮次/来源或本轮文字/文件摘要，并引用短原文；缺乏可引用依据时允许空列表。 |
| reasoning | 非空的简洁判断理由，说明关联及歧义，不输出分析任务答案或冗长探索过程。 |
| basis | `history_continuation`：可见业务历史支持延续；`prior_file_reference`：仅有先前文件操作意图；`none`：均不满足。 |
| result | 严格布尔值；前两类依据必须为 true，none 必须为 false。 |

弱文件引用仅表示操作意图，不代表请求属于业务。即使要求把旧合同作为娱乐素材，也可能为 prior_file_reference；文字 unrelated 在聚合处阻止准入。不能将“不是业务延续”直接等同于“没有文件操作意图”。

v11 在提示词与 Schema 字段描述中同步约束普通前文／文档对象的区别，以及“语义指向明确不等于历史中已找到文件”，要求 reasoning 解释引用条件的原文依据；没有新增字段、改变阈值或调整 SSE。该约束属于模型语义判断，现有结构校验不能保证模型永不混淆，必须配合变体与不同样例组合的真实回归。

history_continuation 的证据必须同时覆盖可见业务历史与当前输入；prior_file_reference 允许只引用本轮文字中的文件指引和操作要求，并说明缺少可见业务历史支持、尚未定位核验文件。不能为凑齐历史证据而编造引文，也不能因用户称它为合同就升级为历史支持。助手历史回答不自动作为权威事实，文件摘要不冒充原文条款。Schema 校验字段及 basis/result 一致性；空历史却声称 history_continuation 会收到明确纠错反馈。程序不能替代语义判断的质量核查。

`node.py` 提供同步 `check_context_relevance` 和原生异步 `check_context_relevance_async`，图装配绑定二者。输入为已选 `context` 任务元组、当前文字与有序文件摘要，不接收页面或文件字节；没有本轮文字且缺少历史或文件摘要时返回 skipped；有文字时允许空历史判断。

调用复用全局 MLLM 配置和并发配额，通过 `create_json_chat_completion` 提交 `schema_name=context_relevance`、`strict=true`、`enable_thinking=true`；思考与最终 JSON 共用全局 max_completion_tokens，不再另设 1200 上限。`max_attempts` 默认 3，允许 1～3 次，不新增环境变量或工具。

只接受正常 stop、无拒答/工具调用、非空且完整的 JSON；重复字段、NaN/Infinity、代码块、缺失/额外字段、空白理由和错误类型均拒收。格式失败以 user 追加具体字段问题和修正要求，同次判断稳定消息不变；全部校验通过或结束时清理整段反馈，原始失败仅保留私有审计，遵循[上下文规范](../../../standard/agent-context-management.md)，不回显无效原响应，不使用 tool-tag 或 system_guidence。

`context_relevance_result` 私有对象保存 completed/failed、已接受的 generation 与 audit；后两者排除普通序列化。只有成功才向 `context_relevance` 写入严格布尔值，并向内部 `context_relevance_basis` 写入依据；跳过或失败时依据为 null。非法历史、请求故障或纠错耗尽返回 failed，取消向上传播，不发布迟到结果。

`context_relevance_feedback` 同步记录程序生成的业务日志；未调度时为空。false 仅说明未确认对话关联或明确的先前文件操作意图，不代表本轮与业务无关；failed 不冒充 false。完整契约见[相关性节点的业务 hint](business-gate.md#相关性节点的业务-hint)；统一拒绝节点会依据这些日志生成 SSE 回复。

## 聚合与服务衔接

上下文按依据分级计分，不再对所有 true 一律给高分。明确的非业务文字不能被上下文或其他关联分救回；信息不足的追问仍允许上下文补足。所有适用分支结束后只聚合一次；分数、阈值、否决和失败优先级统一见[加权与阈值聚合](business-gate.md#加权与阈值聚合)。

正式执行器在激活时读取上述可信历史并传入子图，无需前端提交历史或增加接口参数。门禁全过程继续使用 thinking；拒绝提示先按规整格式流式输出，再同步 rejected 至 SSE、快照与驻留历史，并沿用后台 SQLite 备份。模型依据和审计不进入用户展示事件。
