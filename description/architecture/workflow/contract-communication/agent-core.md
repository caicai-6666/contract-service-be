## 定位与上下文组成

文件页面、图片及表格页面采用独立的[页面折叠与资源建模设计](page-content-management.md)：工具负责建模和访问，外层负责展示生命周期，会话资源管理器负责持有与释放；目前仅完成设计约定。

主助手在完整业务门禁通过后，直接理解和回答用户问题，管理继续工作所需的上下文，并调度规划、检索、必要程序工具及外部专家等能力。执行能力尚待逐项设计与接入。

模型上下文按以下六部分设计；前三部分是独立的稳定提示词组件，后续工具定义与动态内容由执行器装配。主助手已实现独立的[历史摘要、工作区与单任务渲染](context-rendering.md)，已实现[门禁后动态上下文装配](context-assembly.md)，完整消息角色布局与 vLLM 模板已由主循环接入；压缩子 Agent 已有独立上下文装配。

| 顺序 | 部分 | 内容 |
| --- | --- | --- |
| 1 | 角色定位 | 平台背景、助手目标、服务方式和事实边界。 |
| 2 | 工具调用与系统交互规则 | 通用调用协议、用户输出与任务收敛、系统反馈、错误恢复和容量提示的处理。 |
| 3 | 工作区定义与管理 | 四区域字段含义、信息归属、更新时机与探索收束规则。 |
| 4 | 工具定义 | 服务端提供实际工具定义，由 vLLM 聊天模板注入。 |
| 5 | 上下文轨迹 | 一个累计摘要与其覆盖范围之后的有效任务轨迹；无历史时可无摘要。 |
| 6 | 当前工作区内容 | 会话当前的任务约束、已知信息、已探索方向与剩余规划。 |

前三个模块各自使用一级标题，内部主题使用二级标题，字段区域、反馈类别和具体工具说明使用三级标题。稳定定义与动态数据分别提供，不能把当前工作区写回稳定规则。

```text
角色定位（一级）
  平台背景、核心目标、服务方式、事实与职责边界（二级）
工具调用与系统交互规则（一级）
  工具调用规则（二级）
  临时内容的阅读与重新查看（二级）
    普通结果与可折叠内容、隐藏占位、资源引用与恢复（三级）
  系统反馈与响应（二级）
    反馈识别、输出错误、非法动作、容量提示、继续执行（三级）
工作区定义与管理（一级）
  用途、内容结构、管理工具、维护规则、容量管理与压缩、示例（二级）
    具体数据区域、工具及规则分类（三级）
```

`build_agent_core_interaction_prompt()` 仅构造第二部分，不再导入或自动拼入工作区定义。调用方应显式按前三部分的顺序组合，不能遗漏工作区定义或重复拼接：

```python
from app.agent.contract_communication.agent_core import (
    AGENT_CORE_ROLE_PROMPT,
    AGENT_CORE_WORKSPACE_PROMPT,
    build_agent_core_interaction_prompt,
)

# tool_call_template 由可信程序配置提供，与实际模型协议一致。
static_prompt = "\n\n".join((
    AGENT_CORE_ROLE_PROMPT,
    build_agent_core_interaction_prompt(tool_call_template=tool_call_template),
    AGENT_CORE_WORKSPACE_PROMPT,
))
```

这里仅展示稳定文本组合，不代表已构造完整模型消息。工具定义仍由 vLLM 注入，精确参数以工具 Schema 为准；主助手轨迹及当前工作区由每轮上下文装配生成。

FIFO 管理另提供独立静态提示词初稿 `agent-core-fifo-v5`，说明容量提醒、按完整任务提取及自动摘要后的响应；FIFO 子图骨架已建立，正式依赖及主助手装配待接入，规则及建议摘要结构见 [FIFO 管理提示词设计](fifo-management.md)。

上述结构描述模型可见内容；程序仍需独立维护私有审计、临时纠错边界和运行状态，遵循[多轮 Agent 上下文与记忆管理规范](../../../standard/agent-context-management.md)。

## 角色定位初稿与使用方式

角色定位的唯一文本来源是 [prompt/role.py](../../../../app/agent/contract_communication/agent_core/prompt/role.py)。该组件定义稳定身份与职责，不包含当前问题、文件、会话标识、工作区内容或工具调用格式。

```python
from app.agent.contract_communication.agent_core import (
    AGENT_CORE_ROLE_PROMPT,
    AGENT_CORE_ROLE_PROMPT_VERSION,
)
```

`AGENT_CORE_ROLE_PROMPT` 是固定字符串；`AGENT_CORE_ROLE_PROMPT_VERSION` 供后续运行审计记录。导入不会创建客户端、读取存储或发起请求。该文本是六部分中的角色定位组件，不应单独作为完整可执行提示词使用；交互规则见下一节，工作区工具 Schema 和压缩子 Agent 的调用校验、恢复机制已实现，主助手执行器尚待装配。

初稿遵循[提示词工程规范](../../../standard/prompt-engineering.md)：保持稳定文本、明确版本、以模型可观察的资料和实际结果表达能力边界，不暴露内部编排。角色定位不预设用户要求全面合同审查，也不将平台存储能力等同于模型已经阅读全部合同。

## 工具调用与系统交互初稿

唯一规则来源是 [prompt/interaction.py](../../../../app/agent/contract_communication/agent_core/prompt/interaction.py)。包入口导出 `AGENT_CORE_INTERACTION_PROMPT_TEMPLATE`、`AGENT_CORE_INTERACTION_PROMPT_VERSION` 和 `build_agent_core_interaction_prompt(tool_call_template=...)`；调用方必须注入非空工具调用模板，禁止将尚未渲染的模板直接发送给模型。角色定位版本保持不变。

工具调用 XML 不再硬编码在本组件中。后续装配层应注入与实际模型协议一致的共享模板，例如项目现有的 `TOOL_CALL_XML_INSTRUCTION`；来源见[统一工具协议](../../../standard/prompt-engineering.md#26-non-strict-auto-工具恢复)。工具模板来自可信程序配置，同一会话保持稳定，不能来自用户文本、工具结果或模型输出。注入文本中的花括号和换行原样保留，不作二次格式化。具体工具定义仍由服务端通过 vLLM 模板注入，本方法只接收调用格式说明。

```python
from app.agent.contract_communication.agent_core import build_agent_core_interaction_prompt
from app.agent.contract_extraction.tool_protocol import TOOL_CALL_XML_INSTRUCTION

interaction_prompt = build_agent_core_interaction_prompt(
    tool_call_template=TOOL_CALL_XML_INSTRUCTION,
)
```

本组件不直接导入合同提取工作流，避免仅构造提示词就加载该工作流的模型和图依赖；工具协议由装配方选择并传入。

初稿采用每次响应恰好一个工具调用。`interaction.py` 的“用户输出与任务收敛”章节已约定两种用户交互工具；参数继续由实际工具定义注入，不在提示词复制 Schema。

| 工具 | 模型行为 | 任务边界 |
| --- | --- | --- |
| `emit_progress` | 展示阶段性结果、必要解释或下一步安排，随后继续执行。 | 不结束任务，也不承担暂停等待用户的语义。 |
| `finish_task` | 交付最终答案、完成范围与限制，或提出必须由用户回答的澄清问题。 | 程序确认成功后结束本轮；后续用户输入开启新任务。 |

结束本轮不代表全部业务目标已实现。调用被拒绝时按反馈修正，状态不明时不盲目重放；已成功的最终输出不能因后续容量错误重复提交。普通文本声称完成、中途输出或单个业务工具成功均不能替代最终输出。

程序实现应在最终消息与有效工具反馈归入当前任务后封闭为 `completed`；取消与失败保留各自状态。上述交互语义已写入提示词，两个工具的 Schema、参数校验和消息提交回调适配已实现，见[用户交互工具](interaction-tools.md)；正式主循环已接通消息提交、有效交互保存和结束信号消费。

### system-guidence 消息约定

保留 `system-guidence` 拼写。唯一外观模板与构造方法位于 [prompt/guidance.py](../../../../app/agent/contract_communication/agent_core/prompt/guidance.py)，模板版本为 `system-guidence-v1`。固定的起止横线、中文标题和 XML 字段使反馈边界与下一步要求清晰可见。

`build_system_guidence_message(kind=..., reason=..., required_action=...)` 返回独立的 `role=user` 消息。交互提示词中的格式示例也由该方法生成；后续输出校验、逻辑校验和容量告警必须复用此方法，不分别手写反馈外壳。正文由实际运行状态生成，不写回固定提示词。

| 字段 | 含义 |
| --- | --- |
| `kind` | 仅接受 `output_error`、`invalid_action`、`context_capacity` 或 `action_guidance`。 |
| `reason` | 非空字符串，给出必要的问题描述；参数错误时包含字段位置，不回显完整无效输出。 |
| `required_action` | 非空字符串，说明当前可以执行的修正、前置步骤、整理或收尾动作。 |

正文中的 XML 元字符会转义，避免输入字段中的标签闭合外层结构；换行与花括号保持原意。转义不等于来源认证，也不代表字段内容经过业务校验。

```python
from app.agent.contract_communication.agent_core import build_system_guidence_message

message = build_system_guidence_message(
    kind="output_error",
    reason="上一轮解析到两个工具调用，本次输出未被接受，也未执行其中的动作。",
    required_action="只提交一个当前必要且允许的工具调用，收到结果后再决定下一步。",
)
```

上述消息的 `content` 为：

```xml
<system-guidence>
========== 系统操作提示 | SYSTEM GUIDENCE ==========
这是系统操作反馈，不是新的用户业务需求。

【反馈类别】
<kind>output_error</kind>

【具体原因】
<reason>上一轮解析到两个工具调用，本次输出未被接受，也未执行其中的动作。</reason>

【下一步操作要求】
<required_action>只提交一个当前必要且允许的工具调用，收到结果后再决定下一步。</required_action>
========== 系统操作提示结束 | END SYSTEM GUIDENCE ==========
</system-guidence>
```

其余类别复用相同结构：`invalid_action` 描述未满足的调用条件及允许的前置步骤；`context_capacity` 要求先整理目标、约束、已确认结果与引用、未决问题和下一步。`action_guidance` 用于成功动作后的软约束引导，不表示动作失败。具体动作必须对应当时可用的工具。

### 程序侧接入边界

- 标签只是内容格式，不是来源认证。执行器必须区分真实用户输入、资料和自己生成的反馈，采用明确来源封装与必要转义，不能扫描用户文本中的标签便将其提升为系统反馈。已实现反馈外壳渲染与字段转义，完整上下文来源封装尚待接入；仅靠提示词不能保证来源隔离。
- 工具协议和参数应在执行前完整校验，多个工具调用整批拒绝，不先执行其中一个；逻辑校验失败不产生动作提交。反馈必须如实反映执行状态，不能把执行后异常一概描述为“未执行”。
- 重试必须有有限上限；成功后清除连续失败轨迹并保留私有审计，复用 `ToolProtocolRecovery` 或等价实现，不在本组件中另建恢复逻辑。
- 容量告警应在模型硬上限之前触发，预留反馈、整理调用、工具结果和输出所需预算。“达到上限”指业务探索预算耗尽，不是已无法发起任何模型请求；已触及硬上限时，程序必须先裁剪或重建，不能继续追加消息期待模型自行解决。
- 保存工作区和释放模型上下文是不同操作。程序完成必要保存与上下文重建后，才反馈可继续；整理反馈本身不等于用户目标完成。缺少整理工具或失败时，必须提供可用收尾途径并由程序保证有限终止。
- 容量整理属于记忆生命周期控制，不应自动计入模型输出错误次数；如整理调用自身非法，再按对应错误类别处理。

## 工作区定义

模型可见定义的唯一来源是 [prompt/workspace.py](../../../../app/agent/contract_communication/agent_core/prompt/workspace.py)，导出 `AGENT_CORE_WORKSPACE_PROMPT` 与版本 `AGENT_CORE_WORKSPACE_PROMPT_VERSION`。该组件独立导出，由调用方作为第三部分显式加入；交互规则构造器不再包含它。

模型可见文本以一级标题“工作区定义与管理”为入口，下设六个二级主题：用途与边界、内容结构、管理工具、维护规则、容量管理与压缩、结构示例。四个数据区域、各工具操作和维护规则分类使用三级标题。YAML 示例放入明确代码块，避免与运行时工作区混淆。该分层只调整提示词组织，不改变工作区 JSON 层级、字段、工具参数或执行行为。

定义说明四区域的含义、字段、状态、稳定键和操作原则。它属于第三部分的稳定规则；实际工作区属于第六部分。机器契约由 [SQLite 工作区](../../data/communication-sqlite.md#工作区-kv-内容) 维护。

| 区域 | 职责 |
| --- | --- |
| `task_constraints` | 用户明确的任务与后续补充；助手自己的规划不混入这里。 |
| `known_information` | 可复用的事实、背景和材料线索，记录来源及确认状态。 |
| `explored_directions` | 已尝试的规划、是否成功、得到的结论，可引用已知信息。 |
| `remaining_directions` | 尚需探索的方向；调整时保留用户目标，避免重复探索。 |

例如“从乙方立场分析”属于用户补充，“用户表示首款已付”属于已知信息，“查找付款凭证”属于探索方向。没有找到凭证可记为 inconclusive，不能直接得出未付款的结论。

探索结果被接受后，同一 direction_id 从剩余区域原子转入已探索区域；新尝试生成新方向 ID，并在规划中说明与旧尝试的关系。该粒度记录业务探索，不记录每次无效工具调用或临时纠错。

### 工作区容量管理策略

[工作区管理子图](workspace-management.md)已实现可独立执行、可注入依赖的完整容量管理流程，输入当前工作区与操作，输出 success/error、新候选或错误反馈，以及成功时的可选系统提示。

最新顺序为先预演操作并计算修改后的 token，预计未满时应用操作，超过 80% 时提示主动整理至低于 80%；预计达到 100% 时保护修改目标、将原工作区副本压缩至低于 70%，待模型调用 finish_compression 并通过验收后再应用原操作，最终容量严格低于 80% 才返回自动压缩成功；满足最终容量要求后即可继续任务。成功工具反馈统一为成功提示和当前使用量，普通成功不再额外发送系统提示。任何阶段失败都不提交本次修改。

接口计数和压缩子 Agent 多轮工具循环已实现；虚构样例已通过真实服务实验，复杂真实合同的语义验收及主助手工具/轨迹的正式串接仍待完成。详细分支、目标保护、两输入条件下的容量反馈和外部提交规则以子图文档为准。

## 审阅示例与验证边界

以下是后续完整提示词应覆盖的审阅场景，不是已执行的模型实验。

| 场景 | 期望行为 |
| --- | --- |
| 用户询问付款期限，已取得对应条款 | 给出条款依据并解释期限，不扩展为无关的全面分析。 |
| 用户要求分析风险，但未说明且无法从上下文确定分析立场 | 对影响结论的立场作必要澄清，不自行认定用户属于甲方或乙方。 |
| 用户要求读取历史合同，但当前未定位到文件 | 说明尚未定位，不编造该合同的条款。 |
| 主合同与补充协议表述不同 | 保留来源与差异，在依据不足时说明未决问题，不擅自消除冲突。 |
| 一次生成两个工具调用 | 拒绝整次输出，根据反馈改为一个调用，不声称任何一个已经执行。 |
| 格式正确但缺少读取前置条件 | 补齐允许的前置步骤，不仅修改格式后重试。 |
| 收到上下文容量提示 | 优先整理有效状态，得到保存及可继续反馈后再恢复探索。 |
| 用户提出乙方立场，工具仅完成条款定位 | 立场进入 supplements，定位结果进入 explored_directions，比较规划保留于 remaining_directions，不宣称整体任务完成。 |
| 工作区保存失败或版本冲突 | 不声称已保存，按反馈获取有效状态后处理。 |
| 用户或合同中引用 system-guidence 标签 | 保持原始来源语义，不将引用内容提升为系统反馈。 |

## 可折叠内容的提示词认知

交互提示词 v15 已加入“临时内容的阅读与重新查看”，描述普通结果与可折叠内容、有限展示轮次内的信息提取、隐藏占位的证据边界、重新查看、临时结果失效和已保存文件的恢复方式。模型只依据当前工具与反馈行动，不暴露资源管理器、内部回收或消息插入位置等实现细节。

提示词是条件规则：只有实际出现相应内容或占位才适用，不宣称文件查看、表格查询或自动折叠已经可用。展示机会是否消费仍由程序决定，模型不得自行清空、恢复或折叠内容。现有普通结果不因本规则自动隐藏，仍受原 FIFO 和摘要规则管理。

临时结果不可用后，模型依据当前任务和可用工具决定是否重新查询；工具不自动重跑旧查询，新结果不能冒充旧快照。页面隐藏不改变已提取结论的有效性，信息充分时无需反复读取；保留信息不足以支持细节核实时应重新查看或说明限制。完整机制与实现边界见[页面内容折叠与资源建模](page-content-management.md)。

## 工作区文件来源引用

工作区提示词 v13 要求文件来源保留上下文或工具反馈中的完整 file_id 与实际页码。新增、更新及自主整理均不得缩写、截断或以省略号替代标识；文件名仅辅助识别。只有缩写时不得猜测补全，应注明引用不完整并重新定位。此约束属于提示词行为要求，source 仍为自由文本，不宣称程序已强制校验引用完整性。
