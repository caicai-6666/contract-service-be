# 用户消息与上下文设计

> **状态：** 事件层已区分 `cancelled`（手动终止）与 `superseded`（用户调整导致被替代），正式执行器支持取消在途门禁。上下文相关性已按本文边界选择和裁剪历史；第二层核心问答的上下文组装仍未实现。

所属工作流见[合同沟通智能体](readme.md)，系统边界见 [Communication 总体设计](../../system/contract-communication.md)。

---

## 消息意图

普通用户消息用于提出目标；在此基础上，已确认需要区分两类控制意图：

| 意图 | 含义 | 后续模型行为 |
| --- | --- | --- |
| 用户手动终止 | 用户要求停止当前任务。 | 保留问题与终止标记，不继续执行。 |
| 用户补充或方向调整 | 用户补充背景、修改范围或改变目标。 | 根据新要求更新任务并继续处理。 |

手动终止时，模型不再执行原请求；补充或调整时，模型结合新要求更新目标、约束及计划，再继续处理。首次提问不必强行归入这两类。

消息意图与运行状态分开理解：为了应用新要求而中断旧执行，不代表用户取消了整个任务。标签必须伴随具体内容，不能只让模型看到“已调整”却不知道调整了什么。

事件与快照已提供只读 `context_status` 作为后续上下文构造的依据：

| 操作 | 旧轮次执行状态 | 上下文标记 |
| --- | --- | --- |
| 创建接口显式替代旧轮次 | `superseded` | `user_goal_adjusted`（用户目标调整） |
| 取消当前轮次 | `cancelled` | `user_manually_stopped`（用户手动终止） |
| 其他状态 | 不变 | `null` |

标记由执行状态自动推导，同时出现在 `turn.status` 事件和轮次快照中，不由调用方单独写入。被替代标记属于旧轮次；新轮次仍为正常待激活或处理状态，不能继承旧轮次的终止标记。已完成后的普通追问不改写前轮状态。

当前统一驻留轨迹及 SQLite 备份已保存用户输入和任务状态。门禁上下文按最近五轮的轻量契约组装；第二层仍需基于相同原始记录实现自身上下文，不直接使用 SSE 缓存。

## 门禁阶段的用户中断限制

> **已实现：** 业务门禁返回最终判断前，不允许用户终止当前任务；只有完整门禁通过并进入后续执行阶段后，才开放手动取消和方向调整导致的任务替换。目前后续执行可接模拟问答。

- 门禁判断期间，取消接口必须拒绝中断请求；创建新轮次时也不得通过显式替换终止旧轮次，不能用 `superseded` 绕过限制。拒绝操作不得改变旧任务状态、停止旧执行或注册替代轮次。
- 门禁通过并进入第二层后，允许按现有语义取消或替换；门禁拒绝或执行失败时由系统正常结束，不因用户不可中断而阻止系统收尾。
- 关闭页面、断开 SSE 不等于取消，后台继续完成门禁判断；此限制不要求客户端持续保持连接。
- 是否允许中断由服务端 `can_interrupt` 决定，不能只判断 `status=processing` 或 `task.progress.type=thinking`，也不能仅依赖前端禁用按钮。权限更新与取消、替换校验使用事件和历史共享锁；校验不通过返回 HTTP `409`，不修改当前任务。
- 该规则覆盖完整业务门禁，而非仅文件打开、渲染或摘要节点；可读性或摘要完成不提前开放取消与替换。

正式工作流注册后（含待激活阶段）`can_interrupt=false`；完整门禁通过、批准附件且存在后续执行器时改为 true，并追加 `turn.status(status=processing)` 通知前端。此次权限变化不重新激活、不重置计时。拒绝、失败、过期及其他终态均为 false；未接后续执行器时直接正常收尾，不开放中断。系统超时、会话删除、进程关闭不受用户中断限制。通用事件源和独立纯模拟脚本没有真实门禁，保留原有中断行为。

创建响应、SSE 状态、单轮快照及 open/refresh 的任务条目均返回 `can_interrupt`。驻留历史与事件原子更新，终态落库后恢复为 false，不新增 SQLite 列；权限变化随精简 SSE 记录保存。验证覆盖见 `tests/test_communication_interruption.py`、`tests/test_communication_workflow.py` 和 `tests/test_communication_hybrid.py`，不请求真实模型。

## 拒绝任务的统一上下文排除

> **门禁侧已实现，第二层待接入：** `status=rejected` 的历史任务必须整轮排除，此规则同时适用于业务门禁的上下文相关性节点与第二层核心智能体，不只是第二层的过滤规则。

- 排除范围包括用户文字、附件标识与名称、`display_name`、`summary`、文件路径、内部轨迹、拒绝提示及展示事件；不以“保留用户输入”或“只保留拒绝标记”的方式重新注入该轮。
- 后续上下文构造应在程序侧过滤拒绝记录，再渲染模型输入；不能把完整拒绝任务交给模型后要求其自行忽略。生成供这两个消费者使用的累计摘要时也应遵守该边界，避免间接带回被排除的内容。
- 上下文相关性不能以先前被拒绝任务作为当前请求相关的依据。过滤后若没有其他有效上下文，应按无上下文处理，不因用户历史中存在拒绝记录而启用该维度或给予相关性分数。
- 本规则不删除原始历史：拒绝任务仍保存在内存和 SQLite 中，供前端恢复展示；文件准入与不可用状态保持原契约。

门禁侧已在共享锁内从统一驻留历史中排除拒绝任务，并跳过累计摘要，之后才选最近五轮和渲染模型输入；fresh 与已备份记录使用同一规则，见[上下文相关性判断](context-relevance.md)。通用历史读取仍提供候选记录，第二层上下文组装及其累计摘要内容过滤尚待接入，不代表两个消费者均已实现。

## 用户手动终止

已确认：模型上下文只保留该轮用户问题，并附加“已终止”标记；该轮的半段回答、探索规划、中间工具结果和半成品路径不继续进入模型上下文，也不作为正式结果写入长期记忆。

语义示例（不是正式提示词或持久化 Schema）：

```text
用户问题：比较这两份合同的付款条款。
状态：已终止，不继续执行该请求。
```

此前“整轮连同用户问题一起排除”的建议已被后续决定替代，不应按旧建议实现。用户明确重新提出请求后可以再次处理，但不能仅因保留了原问题就自动恢复已终止任务。

推荐保留不可改写的用户原文与独立任务状态，在展示或组装上下文时生成标记；具体字段和序列化格式待定。

模型上下文清理不等于删除所有用户可见历史或私有审计。界面如何保留半段回答、审计保存期限、临时文件如何释放，尚需制定规则。对于只上传文件的轮次，终止后保留什么用户输入摘要也待确定；不得保留已经清理且不可用的路径供后续模型调用。

## 用户补充与方向调整

已确认：原目标不必全部取消。新旧要求冲突时，以用户最新明确要求为准；不冲突的原有要求继续有效。

| 示例 | 对原任务的影响 |
| --- | --- |
| “我们是乙方。” | 补充分析立场。 |
| “只看付款条款。” | 缩小分析范围。 |
| “不用比较了，直接总结第二份合同。” | 改变目标，停止沿旧比较目标推进。 |

是否复用旧执行结果必须考虑其与新要求的适用性，不能默认把旧半成品变成有效结论。已确认用户补充、确认或方向调整作为同一会话下的新轮次输入，使用新 `turn_id` 和新事件流；不恢复已完成的旧轮次。

两种情况必须区分：

- 旧轮次已结束：保留原终态，新输入创建普通新轮次。
- 旧轮次仍在处理：按“用户调整”停止旧执行，以 `superseded` 结束旧流，再按更新要求启动新轮次和新流；不能误记为用户取消整体目标。

模型后续应理解为“旧执行被新要求替代”，而不是“整个目标已终止”。用户原目标与补充内容结合使用，冲突的旧计划和旧半成品不能继续作为权威依据。实际任务控制需停止旧执行、阻止迟到结果污染上下文，而非只断开 SSE。

事件层已原子记录新旧轮次关联、关闭旧流并拒收旧事件，HTTP 创建接口已接收输入及显式替代标识，详见[事件运行时](../../system/communication-events.md)。正式执行器会取消旧门禁协程并拒收迟到结果；门禁侧已读取符合边界的旧输入，旧文件原文复用及第二层上下文继承仍未实现。

助手提出澄清或确认时，本轮以 `final` 消息完成交付并关闭流；该问题应作为后续对话可理解的上下文保留，不应因为整体目标尚未完成就视为用户取消，也不应添加“已终止”标记。轮次 `completed` 与用户手动终止是不同语义。

## 隔离与后续验证

模型可见内容、用户可见历史、执行状态和私有审计不能混为一个无边界的消息列表。实际模型节点的上下文分层与成功后纠错清理遵循[多轮 Agent 上下文与记忆管理规范](../../../standard/agent-context-management.md)，本文件仅补充用户控制语义。

实现时至少验证：取消标记能够阻止自动续做；取消轮次的迟到结果不进入上下文；用户原问题仍被保留；补充信息不丢失无冲突要求；改变目标不沿用冲突计划；不同用户、会话的内容不混入。当前这些业务路径尚未实现和验证。
