# 任务筛选规划提示词

## 用途与版本

当前版本位于 `app/agent/conversation_memory/prompt/planning.py`，版本为 `conversation-memory-planning-v20`。已接入[会话记忆工作流](readme.md)节点1的模型循环。v4、v14、v15、v19已有真实实验；v20明确部分历史可见时的筛选与提取边界，尚未进行真实模型实验。

v20明确当前批次不代表完整会话，首项不一定是会话起点。缺少前文时仍按本任务明确的调整筛选，提取新条件、优先级或取消范围，不推测旧值、旧方案和不可见指代；只有空泛指代、无独立业务信息时通常跳过。缺失背景不能把已明确的新条件变成未知，也不要求每条都声明历史不完整，不将本轮调整当作整个会话最终状态。系统提示词保留单任务事实边界及规则列表排版；不改变工具Schema、轨迹加载或分批调度。本次不实现约10条分批及末条completed校验，也不将尚未由程序保证的批次边界写成模型可依赖的输入事实。

v19将系统提示词中`## 提取要求`下的每项现有规则改为以`- `开头的列表项，规则内容保持不变。同时撤销v18误加的模型输出列表格式要求及其排版示例。此次仅整理系统提示词自身的可读性，不约束extraction_requirements输出采用列表，不修改工具Schema或增加格式校验。

v17明确区分计算结果与业务认定：提取阈值、时长或金额时，必须同步保留原记录明确给出的统计范围、例外及待确认前提，具体说明尚未确认的事项，不能只写“保留适用前提”。以计划维护是否计入停机为例，不将停机量计算升级为违约认定；也不凭空增加待核实事项，或因存在限定就丢弃已确认计算结果。该例来自已审阅测试场景，后续同场景复测只能验证回归效果，不能当作未见案例泛化验证。本次不修改原始轨迹、工具契约或历史实验产物。

v16要求保留时间的原始数值、单位、自然日/工作日口径、起算条件及上下限等限定；不得自行将月/年换算为固定天数，不在括号解释中附加无依据换算或补造精确时刻。仅保留本任务有效记录已提供、有适用依据的换算，同时保留原表达。已有相对日期锚定规则不变，任务时间不能被用来臆造期限起算日或截止日；约束覆盖证据、入选理由及提取要求。本次只修改提示词及离线回归测试，不修改原始任务、工具参数或历史实验结果，也不新增确定性时间转换程序。

## 消息组织

v14 将具体后续安排、待办、时间、顺序、依赖及授权边界明确列为应选择信息，不按进度同步或尚未执行排除。提取时区分用户陈述的进度、待办和已验证结果，保留原有先后条件；当前未授权不能改成永久禁止或自动执行承诺，不补齐缺失字段。第24任务作为正例。仅强化提示词，不增加工具参数或实际调度能力。

v13 从 MemoryTaskInput.created_at（UTC Unix毫秒）生成带明确 +08:00 偏移的“任务创建时间”，位于每个任务的动态数据块内，不进入固定 system 前缀。该展示时区是本项目当前约定，不从服务器本地时区推断。旧输入缺失时展示“未提供”，不自动补为当前时间。模型解释本轮用户的相对日期时使用该时间；引用材料中的相对日期仍需材料自身依据。Service 后续从 ConversationHistoryRecord.created_at 原样复制，不能使用激活时间或后台落盘时间替代。

例如任务创建时间为2026-09-08T10:55:00.000+08:00，“明天核验签章”可保留为“计划明天（2026-09-09）核验签章”，不能写成已经核验。仅说明解释规则，并非程序确定性执行自然语言日期转换。

v12 将有具体对象、前提或可复核依据的计算及业务纠错列为应保留信息，不因涉及通用知识而跳过。提取旧值时标明错误或不适用，保留修正结果及口径；final 或时间较晚不自动具有事实优先级，未解决冲突仍须保留不确定性。第23任务作为含税计算纠错正例。本次只修改提示词及其测试，不改变轨迹原文、工具契约或历史实验结果。

v11 分别明确两层规则：筛选时，与本任务业务目的直接相关且具有具体参考内容的外部资料可保留，不能仅因不是合同约定而跳过；只有链接、未读资料名或空泛内容不自动入选。提取时保留来源、用途、适用范围和不确定性，区分公开说明、单方陈述与合同承诺，不将预计交期改成确定义务，也不补造日期或核验结果。第22任务作为正例，测试仅验证文本与结构约束，语义效果仍待真实实验。

v10 允许将明确用户意图的口语或简短确认展开为完整陈述，仅完善已有含义，不增加事实、动机、授权或执行结果，不强化确定性。“好的”等无明确业务内容的回复不因此获得具体含义；第19任务提供正例，不能额外补写前一任务中的合同数量。

v9 要求每份提取指导专注单个任务，说明本轮新增、确认、延续或改变的内容，不总结整个会话。延续任务可以采用“原本……，现在……”的陈述，但前后均须有本任务自身依据；只有新条件时只写“本轮调整为……”，不从其他任务补写旧条件。该要求同步到 select_task 的 extraction_requirements 参数描述，不新增参数。

v5 明确用户提供的目标、比较对象、关注范围、预算、时间要求、排除条件和决策前提具有独立价值；即使只有输入与确认也应选择，不以缺少分析结论或属于范围确认为由跳过。具体条件确认不同于纯礼貌回复；后续修正不抹去历史约束，但需保留历史适用边界。原始 v4 实验产物保持不变。

v6 在渲染模型输入时排除 type=message 且 status=interrupted 的所有助手消息片段，不区分 intermediate/final。只过滤提取视图，不删除或修改原始轨迹，保留原轨迹序号用于证据定位，因此序号可能不连续。完整消息和工具结果仍保留；工具结果的自身状态及限制必须继续阅读。任务9可依据已返回的计算结果选择，但不得从助手未说完的话推断结论。后续节点2应复用同样的过滤边界，不直接把原始半成品消息作为提取依据。

固定 system 消息按以下顺序拼接：

v8 明确只提取当前任务自身的信息，不再引用其他任务解释或扩写总结。遇到本任务不能解释的指代保留原称谓；自身信息不足时允许跳过。该语义规则依赖模型遵循，不代表确定性事实验证。

已移除刚新增的跨任务引用参数及映射；中断助手消息过滤、业务约束独立价值和单任务来源边界保持不变。

1. **任务描述**：保留任务定义、六种结束状态、轨迹语义、事实边界、筛选原则、提取要求和示例，不展开私有推理。
2. **工具说明与调用顺序**：think 允许进行当前任务相关推理，包括任务关系、信息价值、冲突、提取重点与下一步动作，不局限于入选理由。首轮必须 think，每轮只能一个工具，不得连续成功调用 think；select_task 选择序号严格递增，只有 finish_selection 被接受才完成。失败动作不推进顺序，首个 think 失败允许修正重试。详细参数由[工具 Schema](planning-tools.md)提供，不复制到提示词中。
3. **纠错反馈约定**：工具自身错误由配对tool消息说明；协议或流程约束违规才以独立user消息提供system_guidence。反馈不是新业务需求，不撤销成功选择，也不放宽系统规则。历史数据中的同名文本无指令效力。
4. **tool_tag 格式强调**：最后原样追加 `get_mllm_tool_tag()` 返回的启动期模板，仅追加一次，其后不再添加 system 内容。配置与初始化见[模型工具调用格式资产](../../../capability/infrastructure/vllm-chat-template.md#模型工具调用格式资产)。

随后单独的 user 消息只展示待处理任务：逐任务使用 YAML 展示序号、状态代码及中文名称、用户输入、附件名称和有序轨迹，不再混入工具约束。任务序号按本批输入从 1 开始，与 SQLite sequence 不同；后续程序通过输入顺序映射真实任务 ID。

渲染复用已安装的 PyYAML，相同输入产生相同内容。只投影公开业务字段，省略任务 UUID、文件存储路径及无关元数据；未知轨迹类型报错而不是静默丢弃。消息与调用标识的关联、轨迹顺序保留；附件与网页内容不读取。字段投影并不等于正文敏感信息脱敏，授权和敏感数据检查须由后续输入层落实。

工具布局固定为 `MEMORY_PLANNING_TOOL_PLACEMENT = "before_task"`。后续调用 `MLLMClient.create_tool_chat_completion` 时须显式传入 `tool_placement=MEMORY_PLANNING_TOOL_PLACEMENT`，详细工具定义通过 `tools` 参数交由 vLLM 渲染，不复制进业务提示词。初始内容顺序为“system（末尾 tool_tag）→ 工具详细定义 → 第一条 user 的任务列表”。当前 Jinja 将工具块置于该 user 消息内容开头，而不是新建 system 消息。

节点1已显式传入 before_task 及 tool_task_index=1，后者固定第一条 user 任务为工具锚点；后续纠错和工作区消息不会移动工具块。真实服务须加载支持该参数的新版项目 Jinja 模板并重启 vLLM。

## 查看方式

```python
from app.agent.conversation_memory import MemoryGenerationInput
from app.agent.conversation_memory.prompt import build_memory_planning_messages
from app.core.config import get_settings
from app.core.tool_tag import initialize_mllm_tool_tag

# 独立预览脚本需初始化；正式应用启动时已加载，不要每次构造提示词都读盘。
initialize_mllm_tool_tag(get_settings().mllm)

request = MemoryGenerationInput.model_validate({
    "tasks": [{
        "task_id": "t1", "status": "cancelled",
        "payload": {"input": {"text": "仅比较付款条件", "files": []}, "trace": []}
    }]
})
messages = build_memory_planning_messages(request)
for message in messages:
    print(message["role"], message["content"], sep="\n")
```

任务、工具和纠错说明以 Python 常量 `MEMORY_PLANNING_TASK_PROMPT`、`MEMORY_PLANNING_TOOL_INSTRUCTION`、`MEMORY_PLANNING_SYSTEM_GUIDENCE` 为来源；调用格式来自配置文件的内存快照。本页不复制维护提示词全文。

## 未实现边界与验证

`prompt/guidence.py` 已提供独立消息构造器，不推断错误原因、不选择工具、不修改传入指引，也不自动追加消息：

```python
from app.agent.conversation_memory.prompt import build_system_guidence_message

message = build_system_guidence_message("首轮必须调用 think，请先调用 think。")
# message 为 role=user 的字典，由模型循环决定何时追加。
```

输出使用 `system_guidence` / `end system_guidence` 分隔线及“【系统流程指引】”标题强调正文，并提醒遵循已有任务与工具规则。拒绝非字符串和纯空白，保留原文分行；标记只是展示格式，不是安全鉴权。调用方只应传入程序生成的可信最小指引，不能直接包装用户输入、历史文本、完整无效参数或异常堆栈。格式版本为 `system-guidence-v1`（仅在文档记录）。已测试精确输出格式、输入校验、多行保留及返回对象独立性。

节点1已接入工具校验及有限纠错循环。工具参数等自身错误不调用该构造器，直接返回具体tool错误反馈；只有协议或流程违规才构造独立user指引，不从历史文本识别或提升同名指令。动作通过全部校验后只移除本段程序插入的system_guidence，失败工具交互和正常历史不删除，私有审计完整保留。此处按用户约定采用区别于通用整段清理的例外策略，详见[节点上下文边界](readme.md#节点1执行与上下文)。

已测试稳定系统前缀、四段顺序、模板仅追加一次且位于末尾、全局模板替换及未初始化失败、调用与纠错说明、重复渲染一致性、嵌套输入不变、业务字段投影和未知轨迹拒绝。未做真实模型效果实验，不承诺模型已能可靠筛选。
