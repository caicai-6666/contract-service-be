# Communication 记忆归档与空闲驱逐

## 职责与入口

`CommunicationArchiveService` 已接入正式应用生命周期，以会话为单位协调扫描、分批、调用 [conversation_memory](../workflow/conversation-memory/readme.md)、检索数据入库和安全驱逐。它不生成工作区、不改变原任务状态、不创建上下文截断摘要，也不提供查询接口。

原始轨迹与工作区继续使用[历史服务的后台备份](communication-history.md)，不必等待模型。归档加工独立进行：已经备份的原轨迹仍可能需要筛选、总结和向量化。这两个完成状态不能混为一谈。

---

## 扫描与分批规则

正式应用默认使用以下参数，位于 `CommunicationArchiveService` 构造器；测试可以注入短时间与单调时钟，当前不增加环境变量配置。

| 参数 | 默认值 | 行为 |
| --- | --- | --- |
| `scan_interval_seconds` | 600 秒 | 启动后每十分钟扫描当前驻留会话。 |
| `minimum_batch_size` | 10 条任务 | 不把摘要算作任务。 |
| `idle_scan_limit` | 3 次 | 连续三个有效扫描周期没有活动。 |
| `idle_seconds` | 1800 秒 | 同时满足至少三十分钟实际空闲。 |
| `processing_timeout_seconds` | 600 秒 | 单批图调用超时后取消并保留待处理状态。 |

普通批次从最早未加工任务开始，至少包含十条；第十条不是 `completed` 时，继续包含至遇到的第一条 `completed`。有更多任务则按相同规则继续分批，不足十条或找不到完成结尾的尾部留待下次。任务状态为 `failed` 也可以加工，这与记忆加工本身失败是两回事。

即将驱逐时强制处理剩余尾部：即使不足十条，或者最终状态为取消、调整、失败、过期，也允许作为最后一个批次；绝不包含尚未终止的任务。普通批次仍保留完成结尾要求。

任务按原 `sequence` 排序，不按 UUID 排序。读到活动任务即停止，不跳过它处理更晚任务。扫描先捕获范围，加工时不混入扫描之后的新任务。

每个会话至多一个在途作业。扫描只派发作业，不等待模型；跨会话使用一个模型执行槽，避免多个批次叠加图内并发配额。单会话失败不阻止其他会话继续处理。

## 状态、重启与数据契约

| 状态 | 权威标记 | 含义 |
| --- | --- | --- |
| 原始轨迹已备份 | 驻留层 `_persisted` / SQLite 原记录 | 原问题、附件引用、完整公开轨迹与原计时已有副本。 |
| 记忆加工完成 | `conversation_records.memory_processed_at` 非空 | 已经完成筛选及所需总结、向量化，结果已提交。 |
| 无需向量化但已加工 | 标记非空，检索字段均空 | 未选任务或 `no_memory`，不再重复调用模型。 |
| 尚未加工或加工失败 | 标记为空 | 保留原轨迹，后续扫描继续尝试。 |

新增标记位于原任务表，不新增业务表。初始化时迁移旧表；已有检索文本/向量对的任务确认为已加工，空检索字段的旧任务仍待筛选。加工标记、检索正文和向量都不进入前端轨迹响应。

打开会话仍只驻留最新摘要及后续历史。归档会按需补读该会话 SQLite 中尚未加工的更早任务，避免旧任务因摘要窗口截断而永远漏掉；此补读不扩展前端或问答模型的历史窗口，不读取已存的向量与检索正文。未驻留的会话不会被后台主动打开，重启后尚未加工任务在会话再次打开后恢复调度。

Service 使用原 `record_id` 作为图的 `task_id`；向模型只传冻结任务的原时间、状态和公开 payload，不传用户密钥、工作区或序号分配权。返回内容必须与原记录的身份、payload、状态和计时完全一致。

## 提交与失败边界

1. 在锁外调用图完成筛选、总结和向量化。
2. 完整校验图输出、任务覆盖及顺序；本批任何加工失败则本批不提交，保留原批次在下一扫描重试。图可返回部分成功，但服务当前采用整批提交，避免失败后把原批上下文拆散。
3. 先确认原始备份回执，再在驻留锁内复制最新工作区及其已落库版本。模型加工期间的新工作区可以进入此次快照，但不重新解释其内容。
4. 校验任务引用的 upload 文件。新上传原始字节暂留驻留会话，可恢复缺失文件并校验内容；重启后没有原字节的老文件只验证存在、可读和非空，缺失则阻止归档，不伪造内容。路径必须为已注册 UUID PDF，拒绝越界路径和符号链接。
5. `archive_tasks_with_workspace` 在同一 SQLite 事务提交原轨迹、检索文本、float32 向量 BLOB、加工完成时间和工作区。向量继续执行固定 4096 维、有限且 L2 归一化校验，原 payload 不被总结替换。
6. 事务成功后才确认内存持久化状态，并释放本批附件的暂留字节。磁盘文件及驻留原轨迹继续保留。

数据库事务、文件验证或模型调用失败均不允许驱逐。已完成的此前批次不撤销；失败批次下次重试。数据库提交成功但回执丢失时，下一次读取持久化加工标记跳过已完成批次，不重复模型加工；存储接口也支持相同结果幂等确认，拒绝覆盖不同的已加工结果。

原始备份、归档提交、删除和驱逐共用备份协调锁；模型调用期间不持有它，也不持有驻留锁。删除后迟到结果不能重新创建会话；同 ID 的新驻留实例也不能接收旧实例的归档结果。

## 驱逐信号与最终检查

每个驻留会话有 `residency_id`、`activity_generation`、最后活动时间和连续空闲扫描次数。注册新任务、任务进入终态、工作区更新、用户打开或向前刷新会话都会更新活动信号并重置空闲计数。待激活或处理中的任务阻止空闲计数。重复调用扫描接口不等于经过多个十分钟周期。

驱逐作业捕获实例 ID 与活动代数。所有加工、文件检查和落库结束后，最终在同一驻留锁内比较并删除，必须同时满足：

- 仍是原驻留实例，活动代数未改变。
- 没有活动任务、未备份轨迹或未确认的备份副本。
- 数据库没有该会话尚未加工的任务，当前驻留任务全部具有加工完成标记。
- 内存最新工作区已同步落库。
- 当前驻留轨迹引用的附件通过检查。

加工期间来了新输入时，只取消本次最终驱逐，已成功归档的旧批次仍保留；不将新轨迹误标为已处理，也不覆盖新工作区。即使新输入恰好在最后文件检查期间到达，锁内比较仍能保护它。

驱逐只释放内存的历史、工作区、附件字节和该会话事件运行时，不删除 SQLite 行或 upload 文件。之后通过 open 从 SQLite 恢复历史与工作区，实时 SSE 事件源不重建。

## 生命周期与验证

正式 `app/bootstrap.py` 构建并暴露 `application.state.conversation_memory_graph` 和 `communication_archive_service`。依赖初始化完成后启动扫描；关闭时先取消扫描和模型作业，再停止事件生产，最后备份原轨迹与工作区。关闭不等待十分钟周期，也不强制调用模型；已备份但未加工任务保留空标记，可在后续重新打开会话时恢复。

独立 `scripts/serve_communication_demo.py` 仍是无模型、临时数据库的样式展示服务，不启用此归档调度。正式应用即使启用了展示事件生产者，也使用正式归档链路。

测试入口：

```bash
python -m unittest discover -s tests -p 'test_communication_archive.py'
python -m unittest discover -s tests -p 'test_communication*.py'
python -m unittest discover -s tests -p 'test_memory*.py'
```

覆盖分批边界、短尾强制处理、实际空闲时间、活动阻塞、两个阶段的新输入竞态、工作区更新、删除防复活、迁移和重启、模型/数据库失败、回执丢失、附件恢复和缺失、定时器启动与取消；另以真实编译的 LangGraph 配合模拟 MLLM/Embedding 响应，验证完整图到真实临时 SQLite 的总结与向量落盘，不使用真实业务库或依赖在线模型。
