# 合同交易类别定义结构

> **用途：** 本文定义合同分类节点可读取的权威交易类别 YAML 契约。类别目录只描述“什么交易属于该类别”，不保存模型输出、RAG 示例或分类运行状态。

合同类别位于[类别定义目录](../../../data/definition/contract-category)。每个类别使用一个以 kebab-case `code` 命名的独立子目录，子目录中的 `definition.yaml` 是该类别唯一权威定义；专家确认的正例和反例卡片分别存入 `positive/` 与 `negative/`。

```text
data/definition/contract-category/
  sale/
    definition.yaml
    positive/
      card-001.yaml
    negative/
      card-001.yaml
  work/
    definition.yaml
    positive/
      card-001.yaml
    negative/
      card-001.yaml
```

> **文件职责：** 加载类别规则时只读取 `definition.yaml`；`positive/` 和 `negative/` 只保存该类别的专家样例。示例卡片不是类别定义，不得覆盖、扩展或修改权威语义。

卡片由两类依据组成：优先使用 `real-data` 合同语料整理并脱敏；真实语料缺少的类别，依据权威定义和相邻类别边界补充规范化场景。规范化场景只用于表达可执行边界，不能声称来自真实合同。卡片不保存来源 PDF 标识、当事人名称、版本或重复的类别标签；目录名决定目标类别，`positive/` 或 `negative/` 决定正反标签，文件名只提供稳定排序。所有卡片进入正式生产提示词前仍应经过业务专家终审。

---

## 分类维度

当前目录定义的是合同中的**交易类型**，判断依据是当事人之间的核心权利义务交换。框架协议、订单、补充协议等文档形态，以及制造、软件、金融等业务领域，不与交易类型混在同一类别目录。

目录当前包含 25 个实体类别：19 个民法典典型合同类别和 6 个企业合同补充类别。应用启动时全量加载并校验目录，分类节点对每个类别分别执行二元判定。当前 YAML 是分类提示词与程序校验的权威输入。

> **多标签边界：** 类别 code 表示合同中存在相应权利义务结构，不是对整份合同作唯一法律定性。同一合同包含多个独立交易时可以命中多个类别；同一复合交易分别完整满足多个类别的核心结构，且相邻边界明确允许共同成立时，也可以多标签。标题、主体经营范围和普通附随条款仍不能单独触发类别。

分类结果不生成主类别、次类别或法律适用结论。`matched` 只说明当前 PDF 证据满足项目定义的交易结构，不能替代律师或法院对合同性质、效力和法律适用的判断。

## 权威依据与项目转换

类别的法定核心结构优先依据现行法律，项目只把它转换成便于证据提取的 `meaning`、`core_exchange` 和边界规则：

- 《中华人民共和国民法典》第五百九十五条规定买卖的核心是出卖人转移标的物所有权、买受人支付价款；第七百七十条规定承揽的核心是承揽人按照定作人要求完成并交付工作成果、定作人支付报酬。完整条文见[最高人民法院公报民法典文本](https://gongbao.court.gov.cn/Details/dfe439fb9450f0525bd7e7b50a6242.html)和[最高人民法院知识产权法庭民法典文本](https://ipc.court.gov.cn/zh-cn/news/view-371.html)。
- 《中华人民共和国民法典》第四百六十七条允许无名合同参照最相类似的典型合同规则，说明现实交易不必被标题强制塞入唯一典型合同；条文见[人民法院民法典全文](https://www.sdcourt.gov.cn/dyzy/372897/xfsd57/6177956/index.html)。
- 《最高人民法院关于适用〈中华人民共和国民法典〉合同编通则若干问题的解释》第一条要求结合相关条款、合同性质和目的、习惯、诚信原则、缔约背景及履行行为解释合同，项目据此禁止只按标题、别名或单一关键词分类；见[最高人民法院公报](https://gongbao.court.gov.cn/Details/f4722cf61c92a585f04b2ecd334f5b.html)。
- 劳动与用工类别以用人单位和劳动者建立劳动关系为边界，依据[《中华人民共和国劳动合同法》](https://www.mohrss.gov.cn/xxgk2020/fdzdgknr/zcfg/fl/202011/t20201102_394622.html)和[《中华人民共和国劳动法》](https://www.mohrss.gov.cn/SYrlzyhshbzb/zcfg/flfg/201601/t20160119_232110.html)。保险、知识产权等补充类别应继续以各自现行专门法律为上位依据。

法律条文决定类别成立所需的核心权利义务，项目的多标签规则只决定检索与下游处理需要保留哪些已被证据支持的结构。不得把“允许多标签”改写成“只要存在相似表象就全部命中”。

## 标准结构

```yaml
code: sale
name: 买卖
aliases:
  - 采购
meaning: 一方转移标的物所有权，另一方支付价款的交易。
core_exchange:
  provider_obligation: 交付标的物并转移所有权
  counterparty_obligation: 接收标的物并支付价款
includes:
  - 标准商品采购
  - 同时满足设备所有权转移的定制设备交易
excludes:
  - 只有加工成果与报酬、没有独立所有权转移和货物价款
distinguish_from:
  - category: work
    rule: 定制设备同时形成成果承揽与设备所有权买卖时允许共同命中。
evidence_hints:
  strong:
    - 明确约定数量、价款、交付和验收
  insufficient:
    - 标题中单独出现采购
```

| 属性 | 形式 | 职责 |
| --- | --- | --- |
| `code` | snake_case 字符串 | 程序使用的稳定类别身份，目录内唯一；其 kebab-case 形式必须等于父目录名。 |
| `name` | 非空字符串 | 面向模型和人工审核的标准中文名称。 |
| `aliases` | 一维字符串列表 | 常见标题和叫法，只帮助发现候选，不能作为充分证据。 |
| `meaning` | 非空字符串 | 类别的正向语义定义。 |
| `core_exchange` | 两项对象 | 分别描述提供方与相对方的核心义务，是分类的主要判断依据。 |
| `includes` | 一维字符串列表 | 应当纳入本类的典型交易结构。 |
| `excludes` | 一维字符串列表 | 说明当前类别必要结构不成立的情形；不得仅因另一个类别也可能成立就排除当前类别。 |
| `distinguish_from` | 类别边界列表 | 引用另一个有效 `code`，说明仅命中一方或允许共同命中的条件；允许为空列表。 |
| `evidence_hints` | 强弱证据对象 | `strong` 提示有力证据，`insufficient` 防止仅凭关键词分类。 |

## 示例卡片结构

每个 YAML 文件只表达一个判断示例，字段顺序固定为场景、证据、理由：

```yaml
scenario: 客户提供原材料，只委托对方按图纸完成加工。
evidence:
  - 客户提供材料和图纸，承接方只收取加工报酬。
  - 没有独立标的物所有权转移和对应货物价款。
reasoning_summary: 只有承揽结构，没有独立买卖结构，因此不命中买卖。
```

| 属性 | 形式 | 职责 |
| --- | --- | --- |
| `scenario` | 非空字符串 | 概括模型需要判断的脱敏真实场景或规范化交易场景；不得包含来源文件标识或当事人身份。 |
| `evidence` | 一至三项字符串列表 | 只列支持当前正反判断的短证据，必须先于理由出现。 |
| `reasoning_summary` | 非空字符串 | 解释证据如何落到目标类别边界，不重复标签或无关案情。 |

卡片不得增加 `schema_version`、`source_pdf_id`、`target_category`、`label` 或来源类型字段。来源层级由本文件统一记录，不把提示词不需要的治理信息重复注入模型。同一事实可以为不同目标类别提供不同边界示例，但每张卡片只能表达一个目标类别下的一次判断。复合交易若同时满足两个类别，应分别在两个类别的 positive 目录提供卡片，并在理由中明确“本卡片只证明当前类别结构”，不能把另一个合法命中当作反例。

> **扩充下限：** 每个类别至少维护三张正例和三张反例。真实数据不足时，新增场景必须同时满足权威 `meaning`、`core_exchange` 和 `evidence_hints.strong`，反例必须命中 `excludes`、`distinguish_from` 或 `evidence_hints.insufficient` 中的明确边界，禁止只替换主体名称生成近义重复卡片。

## 目录组成

| 分组 | 类别 |
| --- | --- |
| 典型合同 | 买卖，供用电、水、气、热力，赠与，借款，保证，租赁，融资租赁，保理，承揽，建设工程，运输，技术，保管，仓储，委托，物业服务，行纪，中介，合伙 |
| 企业合同补充 | 一般服务，劳动与用工，保险，知识产权交易，股权与投资，债务重组与和解 |

`other` 不属于合同类别目录。若完整类别组合仍不能覆盖合同的主要交易结构，分类结果通过 `unmapped` 状态表达，并额外生成一段自然语言交易类型描述供下游使用；描述不是候选类别，不自动写入定义目录。`unmapped` 不得与任何已知类别同时出现。`not_a_contract` 和 `insufficient_evidence` 也属于分类结果状态，而不是合同类别。

## 加载与注入约束

应用启动加载目录时必须：

1. 只扫描每个一级类别目录中的 `definition.yaml` 建立完整可选目录；分类请求按 `code` 确定性调度，每次只注入当前类别定义。
2. 校验父目录名、`code`、顶层属性、嵌套属性和跨类别引用，遇到缺少定义、未知字段或未知类别引用时启动失败。
3. 当前类别定义之后依次注入 `positive/` 正例和 `negative/` 反例；同类卡片按文件名确定性排序，定义是权威规则，示例只用于边界校准。
4. 保留目录内容指纹，确保实验与生产结果可以回溯到具体类别快照。
5. 分类输出遵循“证据 → 推理摘要 → 最终决定”，定义文件本身不保存模型证据和决定。

分类节点不得在类别根目录使用 `*.yaml` 将定义与卡片混读。正反例标签由所在目录确定，因此卡片无需重复保存目标类别和正负标签。加载器必须校验卡片只包含 `scenario`、`evidence` 和 `reasoning_summary`，并按文件名确定性排序。

加载器实现位于 `app.agent.contract_extraction.subgraph.classification.catalog`，对象契约位于同包的 `definition` 模块。`ContractCategoryDefinition`、`ExpertExampleCard` 和 `ContractCategory` 分别表示权威定义、单张卡片和一个类别的完整资料；`ContractCategoryCatalog` 表示整个只读内存快照，并保存根目录、按 `code` 排序的类别对象和 `content_sha256` 内容指纹。

目录路径由 `CONTRACT_CATEGORY_DEFINITION_DIR` 配置，默认指向 `data/definition/contract-category`，相对路径统一按项目根目录解析。FastAPI 生命周期在创建共享外部客户端前完成加载，并将对象保存为 `application.state.contract_category_catalog`。缺少目录、布局异常、文件不是 YAML、Schema 不匹配、正反例不足三张、目录名与 `code` 不一致、重复 `code` 或未知跨类别引用都会阻止应用启动；运行期间不重新扫描目录，也不原地修改快照。

分类节点和上下文位置见[合同分类子图](../workflow/contract-extraction/classification.md)，提示词顺序与缓存边界见[提示词工程规范](../../standard/prompt-engineering.md)。

## 当前验证

当前目录已经完成 YAML 解析、目录级一致性检查、真实语料卡片建设和缺失类别的定义驱动扩充：

- 25 个类别目录分别包含一个 `definition.yaml`、一个 `positive/` 和一个 `negative/`，对应 25 个唯一 `code`。
- 类别父目录名均与 `code` 的 kebab-case 形式一致。
- 所有文件具有统一字段及字段顺序。
- `distinguish_from.category` 均引用目录内真实类别，不存在自引用。
- `aliases` 不包含文件内重复值。
- `real-data` 共盘点 183 份 PDF，按文件字节去重后为 179 份；其中 97 份正文可提取字符少于 100，扫描件不能仅凭文件名作为卡片证据。
- 示例卡片共 173 张，其中正例 89 张、反例 84 张；25 个类别均达到至少三张正例和三张反例。
- 正例底稿覆盖约 33 份互不重复合同。买卖与承揽各有 6 张真实语料卡片，并各增加 1 张定义驱动的定制设备复合交易卡片；建设工程和技术各 5 份，运输与一般服务各 4 份；租赁、保险和知识产权交易按语料实际可核实数量分别保留 1、1、2 张正例。
- 主要相邻类别的反例增加至四至五张；语料未覆盖类别保留一至两张真实边界反例，不用同一事实改写出大量近义卡片。
- 89 张卡片来自真实语料归纳；84 张属于定义驱动卡片，其中正例 55 张、反例 29 张，用于补齐真实数据没有覆盖的典型结构、相邻类别边界和复合交易共同命中规则。

`real-data` 当前仍没有足以独立证明行纪、保管、债务重组与和解、劳动与用工、股权与投资、保理、融资租赁、赠与、保证、中介、借款、委托、合伙、物业服务、供用能源或仓储的合同。这些类别现有正例属于定义驱动的规范化场景，不计入真实语料覆盖率；后续获得对应合同时，应优先补充真实卡片，并由专家决定是否替换规范化卡片。

目录加载器、正式 Pydantic Schema、内容指纹、启动生命周期接入和逐类别并发判定已经实现，并由真实目录加载、跨类别引用失败、FastAPI 生命周期、并发命中/未命中和工具纠错测试覆盖。分类节点从应用级内存快照接收目录对象，不会自行重复读取 YAML。当前卡片完成了全量语料盘点、分层抽样、缺口扩充和结构校验，尚待业务专家终审。
