# 已批准删除申请后台执行

定时扫描[删除审核库](../../architecture/data/deletion-review.md)，正式删除审核明确批准的合同，并记录执行结果。由 `app/bootstrap.py` 启动和关闭，实例保存在 `app.state.deletion_review_executor`；无需等待中间件登录。

---

## 执行顺序与清理范围

`DeletionReviewExecutor` 位于 `app/service/deletion_review_executor.py`。每轮扫描通过 `scan_once()` 执行，返回本轮成功记录的删除完成数量。

1. 首轮扫描将上次进程遗留的 `deleting` 申请恢复为可重试状态。
   每轮扫描同时通过申请服务协调合同 can_delete 标志，补齐跨库写入中断或拒绝后的恢复；单条协调失败不阻止其他合同处理。
2. SQLite 短事务领取 `review_status=approved`、已有反馈消息 ID、执行状态为 `pending/failed` 且已到重试时间的申请，增加尝试次数。
3. 调用现有 `ContractIngestionService.delete_document()`，在合同锁内核对申请时的入库时间及通行证，防止旧审批误删同一 PDF 后来重新入库的合同。
4. 正式元数据进入 `deleting`，依次删除 Neo4j 合同节点及全部关联边、ES 文档、正式 PDF，最后删除 SQLite 合同元数据。
5. 保存 `deletion_status=succeeded`、完成时间，保留申请快照和审核备注。

SQLite 外键级联删除该合同的注意事项、类别关联；已有 FTS 删除触发器同步删除合同名称、摘要、注意事项的索引，随记录保存的向量一并移除。共享类别定义、用户记录不属于合同删除范围。

入库审核区的旧快照与会话历史遵循各自生命周期，不随正式合同删除。删除审核记录在本地处理完成后由[独立清理服务](deletion-review-cleanup.md)按保留期清理；保存的原 PDF 地址在正式删除后不可再读取。

## 重试、恢复与关闭

审核结果和实际删除状态分开保存：`approved` 表示允许删除，只有 `deletion_status=succeeded` 表示本地执行完成。

| 情况 | 行为 |
| --- | --- |
| 待发送、待审核、拒绝或缺少反馈消息 ID | 不执行删除。 |
| ES、Neo4j、PDF 或正式 SQLite 删除失败 | 保存 `failed`、脱敏错误类型与下次重试时间；其他申请继续执行。 |
| 正式合同身份与申请快照不一致 | 拒绝删除并记录失败；不触碰外部存储。 |
| 图节点、ES 文档或 PDF 已不存在 | 由现有删除服务按幂等完成处理。 |
| 正式元数据已不存在 | 元数据是最后删除的部分，因此按已完成记录结果。 |
| 外部删除结束，但审核库暂时不可写 | 内存保留待保存结果，下轮先重试写入结果，不重复外部删除。 |
| 执行期间进程退出 | 下次启动恢复已领取申请；正式库已有 `deleting` 恢复机制继续未完成清理。 |

正式库与审核库没有跨库事务，依靠领取状态、正式删除顺序和幂等重试恢复。每个应用实例只有一个执行任务，同实例扫描通过锁串行；当前按单 worker 部署，不支持多个实例同时对同一审核库执行启动恢复。

服务关闭时停止领取新申请，等待当前删除及结果保存结束，再由应用释放 ES、Neo4j 等依赖。日志只记录申请 ID、合同 ID 和异常类型，不写入原始异常响应或凭据。

## 配置与已有数据

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `DELETION_REVIEW_SCAN_INTERVAL_SECONDS` | `30` | 扫描间隔，有限正数秒。 |
| `DELETION_REVIEW_RETRY_SECONDS` | `60` | 删除失败后的重试间隔，有限正数秒。 |
| `DELETION_REVIEW_BATCH_SIZE` | `10` | 每轮最多领取的申请数，正整数。 |

初始化为已有删除审核表补齐执行字段，默认 `pending`。历史已批准且保存反馈消息 ID 的申请会在服务启动后进入扫描范围；已完成的申请不再领取。

删除申请 HTTP 接口已改为[保存申请并禁止重复申请](../../api/contract.md#删除正式合同)，申请服务协调 can_delete 切换与拒绝恢复；本执行器负责批准后的实际删除，独立清理服务负责已完成审核数据。中间件发布与反馈拉取尚未接入。

## 验证

`tests/test_deletion_review_executor.py` 使用临时 SQLite 和实际临时 PDF，模拟 ES 与 Neo4j，验证清理范围、批准筛选、失败隔离与延迟重试、重启恢复、结果写入失败、重新入库身份保护、扫描批次和关闭等待，以及旧表字段升级。测试不删除实际业务合同。
