# PDF 页面压缩工具

> **用途：** 本能力文档说明 `app.tool.pdf_page` 如何将 PDF 页面渲染为适合多模态模型输入的 PNG，并按视觉 token 预算等比缩小。

---

## 使用边界

该工具只处理 PDF 页面、图像尺寸和视觉 token 预算，不了解字段定义、提示词、工作流状态或模型请求。`app.agent` 负责调用工具并将结果组装为多模态输入。

默认配置为：最大渲染比例 `2.0`、视觉 patch `32×32` 像素、单页最多 `2048` token。对当前 A4 测试合同，`2×` 渲染约占 `2014` token，因此不会因预算而缩小。

---

## 接口

| 接口 | 职责 |
| --- | --- |
| `compress_pdf_page` | 渲染指定的一页 PDF，返回 PNG 字节、实际尺寸、渲染比例和 token 数。 |
| `compress_pdf_pages` | 按原始页序渲染整份或指定页面。 |
| `estimate_visual_tokens` | 根据图像尺寸与 patch 大小估算视觉 token。 |

单页 token 估算公式如下：

```text
ceil(width_pixels / patch_size) × ceil(height_pixels / patch_size)
```

Agent 不再使用固定的单次视觉预算。MLLM 默认上下文窗口为 `65536` token，先扣除最大生成、公共提示词以及多轮工具历史预留，得到 `43008` token 的视觉容量上限。实际请求预算随 PDF 页数增长：

```text
min(视觉容量上限, PDF 页数 × 单页视觉上限)
```

短合同只使用必要的上下文；页数增加时可以使用更多视觉上下文，直到容量上限。若整份 PDF 按原始分辨率会超限，预处理节点把视觉容量等分为动态单页预算，并对每页保持长宽比缩小。当前普通 A4 页以 `2×` 渲染约占 `2014` token，因此21页约占 `42294` token，可完整放入一个 `65536` 上下文请求。

---

## 验证要求

- 每页结果必须不超过 `max_visual_tokens_per_page`。
- 页码必须从 1 开始、严格递增且不能重复。
- 整份 PDF 的 token 总数不得超过该 PDF 的动态请求预算。
- 工作流复用同一合同页面时，应复用同一份渲染结果与页序，保证多模态公共前缀稳定。
